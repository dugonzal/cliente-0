What to read in it

  Sections 1 and 2 — data read over v3 with authPriv at two key lengths: SHA-256/AES-128 and
    SHA-512/AES-256. Both answer, and the values are the simulated device's.
  Section 3 — a full walk of the MPLS subtree (mplsStdMIB 1.3.6.1.2.1.10.166): 48 lines, no
    parser warnings, exit 0. MPLS-TE tunnels, LSR in/out segments, LDP peers and sessions,
    L3VPN VRFs.
  Sections 4a-4e — the five USM failure reports, each one provoked by the standard client and
    each one read back against the RFC 3414 section 5 counter the agent keeps for it. The
    client's own words, in order: "Unknown user name", "Authentication failure (incorrect
    password, community or key)", "Decryption error", "Unsupported security level",
    "Not in time window".
  Section 4f — the case that is not one of the five, kept because it is the one that
    surprises: an authPriv request for a user configured without privacy cannot be decrypted
    before the level is judged, so the agent counts it as a decryption error. Counted, not
    hidden.
  Section 5 — with good credentials it still reads after all five, so the failures were the
    attempts and not the device.

  The counters are a second, independent read: a snmpget on 1.3.6.1.6.3.15.1.1.x.0. The
  simulator exposes its engine counters to GET, which a hardware device usually does not —
  that is how each failure is tied to its counter here, instead of taking the client's word
  for it. usmStatsUnknownEngineIds also climbs, because every fresh client invocation does
  v3 engine discovery first; that is the protocol working, not a failure.

What a reader can and cannot check

  Can: that the log is internally consistent — each failure moves exactly the counter that
  belongs to it, the exit codes match, and the client's wording matches the counter names.
  Cannot: re-run it. Producing it needs the simulator and a signed token, and this repository
  contains neither.
